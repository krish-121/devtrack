# Database foundation

Phase 2 follows PROJECT_SPEC.md sections 21–24, 42–43, 51–52, 55, 61, 65, and 94.
PostgreSQL stores the data; Prisma describes the model and generates typed access.
The API has one client in `apps/api/src/database/prisma.ts`. The Phase 3 project
repository now reuses it; controllers contain no database queries. This document
describes the Phase 2 foundation. See [API.md](API.md) for the project endpoints
and their authenticated ownership boundary.

## Tables and relationships

```text
User 1 ─── many Project 1 ─── many Task
User 1 ─── many Session
```

A table holds rows of one entity. Columns hold each row's fields. Every row has
a UUID primary key, generated by PostgreSQL's `gen_random_uuid()`. UUIDs are
stable identifiers, not authorization: project repository queries also scope
records to the authenticated owner. Phase 5 added the Session table.

| Table     | Fields                                                                                                                 |
| --------- | ---------------------------------------------------------------------------------------------------------------------- |
| `User`    | `id`, `name`, `email`, `passwordHash`, `createdAt`, `updatedAt`                                                        |
| `Project` | `id`, `ownerId`, `name`, optional `description`, `createdAt`, `updatedAt`                                              |
| `Task`    | `id`, `projectId`, `title`, optional `description`, `status`, `priority`, optional `dueDate`, `createdAt`, `updatedAt` |
| `Session` | `tokenHash` (primary key), `userId`, `expiresAt`, `createdAt`                                                          |

Prisma and PostgreSQL both use camelCase column names, matching the TypeScript
conventions and the specification's SQL example. PostgreSQL identifiers with
capitals need double quotes in SQL.

`Project.ownerId` references `User.id`. `Task.projectId` references `Project.id`.
These required foreign keys prevent orphan projects/tasks even in direct SQL.
Tasks inherit ownership through their project; no duplicate task owner exists.

`Session.userId` references `User.id` with a deliberate delete cascade. A browser
holds a random 256-bit bearer token in an HttpOnly cookie; only its SHA-256 hash
is stored in the table. Sessions expire after seven days; expiration is checked
on every request. Logout removes the row and login removes that user's expired
sessions. Indexes support user and expiry queries. The session migration adds
an expiry-after-creation CHECK constraint. Token hashing is distinct from the
slower Argon2id hashing used for human passwords. No AUTH_SECRET is needed for
this opaque session design; token randomness supplies the secret and the database
holds its validity. Tokens are not signed or encrypted custom payloads.

Task create/update/delete and the parent's updatedAt change share a transaction.
The repository locks the owned project before changing its task, consistently
ordering locks with project deletion. Search/status/priority conditions stay
inside owner-scoped Prisma queries.

## Constraints and deliberate choices

- Email is unique. Writers normalize with `trim().toLowerCase()` before
  persistence; the database rejects email that is empty, mixed-case, or has
  surrounding spaces. A CHECK constraint is a guard, not a normalizer or an
  email-format validator. Future request validation remains a Zod responsibility.
- User/project names, task titles, and password hashes are required and must
  contain more than ordinary spaces. Descriptions and due dates are nullable.
- PostgreSQL enums restrict status to `TODO`, `IN_PROGRESS`, `DONE` and priority
  to `LOW`, `MEDIUM`, `HIGH`. New tasks default to `TODO` and `MEDIUM`.
- Deleting a project **cascades** to its tasks. Deleting a user is **restricted**
  while that user owns projects. V1 uses hard deletion; no archive flag exists.
- Timestamps use `timestamptz(3)` so they represent instants, preserving UTC
  meaning even when input includes an offset. Prisma returns JavaScript dates;
  future API responses will use ISO-8601 strings.
- PostgreSQL supplies creation/default update timestamps. Prisma's `@updatedAt`
  maintains update timestamps for Prisma writes. Direct SQL updates must set
  `updatedAt` explicitly; it is not a PostgreSQL trigger.
- Unique email creates an index. `ownerId` and `projectId` indexes support the
  ownership/project lookups and foreign-key deletion checks. Additional filtering
  indexes can follow actual query needs.

An index helps find matching rows without scanning the whole table. A unique
index also rejects duplicates. A transaction groups writes: every write succeeds
or none of them is committed. The seed uses a transaction to avoid partial data.

The initial migration contains extra SQL CHECK constraints that Prisma's schema
language does not represent. Preserve them in later migrations and review SQL;
do not replace migration history with `db push`.

## Local PostgreSQL

1. Install dependencies with `npm ci` (which also generates Prisma Client).
2. Copy `.env.example` to `.env`; keep `POSTGRES_PASSWORD` and `DATABASE_URL` in sync.
3. Start Docker Desktop's Linux engine.
4. Run `npm run db:up`, `npm run db:migrate`, then `npm run db:seed`.

Compose starts PostgreSQL 18.6 only. `db` is bound to `127.0.0.1:5432`, database
`devtrack_dev`, user `devtrack`. Data lives in a named volume mounted at
`/var/lib/postgresql`, the official PostgreSQL 18 image's volume location.
`npm run db:stop` preserves development data. Do not remove that volume unless
you deliberately want to lose the development database.

Changing the password in `.env` does not change credentials in an existing
PostgreSQL volume. Update the database role deliberately and then the URL.
If a port is occupied, stop the conflicting local service or update the Compose
port and matching URL together. The test service also reserves loopback port 5433.

The example credentials are public local defaults only. Never reuse them for
hosted databases or put real credentials in Git. No hosted database is provisioned
by this phase; future production connections come from environment secrets.

## Migration workflow

`prisma/schema.prisma` defines the current model. `prisma/migrations/` records
the SQL history; `_prisma_migrations` records which migrations a database applied.

For a normal schema change:

```sh
npm run db:format
npm run db:validate
npm run db:migrate -- --name describe_the_change
npm run db:generate
npm run db:status
```

Review the generated SQL before committing. When custom SQL is needed, first
create the migration with `npm run db:migrate -- --name describe_the_change --create-only`,
edit/review its SQL, then run `npm run db:migrate` to apply it. Never edit a
migration after it has been applied to a shared database; create another one.

`migrate dev` uses a temporary shadow database to check migration history and
schema drift. The local Compose role can create it. This command is for
development only and may ask to reset data when history/drift conflicts exist.
Do not accept a reset without understanding what data would be lost.

Prisma 7 does not generate the client or seed implicitly after migrations.
`db:generate` is explicit after schema edits; `db:seed` is always explicit.
See the official [migration command](https://www.prisma.io/docs/cli/v7/migrate/dev)
and [seeding documentation](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/seeding).

## Development seed

`prisma/seed.ts` checks for `NODE_ENV=development`, runs the seed, then disconnects
even after failure. `seed-data.ts` upserts one user, two projects, and five tasks
in a transaction. Fixed UUIDs identify only demo records; empty update objects
preserve edits on repeat runs. Deleted demo records are recreated, so seeding is
an explicit action rather than part of application startup.

The tasks cover every status/priority and include both missing and UTC due dates.
Their Harness/deployment titles are sample data, not implemented functionality.
The demo email is `demo@devtrack.example`. Its password is random, immediately
discarded, and stored only as an Argon2id hash. There is no known demo password
and no login implementation. Reruns preserve the stored hash.

## Tests and cleanup

```sh
npm test
npm run test:integration
```

Unit tests need no database. Integration tests start the opt-in `db-test` Compose
service, wait for readiness, apply the checked-in migration using `migrate deploy`,
then run Vitest. This includes existing HTTP tests and real database/seed tests.

The test database is always `devtrack_test` at `127.0.0.1:5433`, with public test
credentials. Both the runner and Vitest use `apps/api/test/environment.ts` and
override inherited `DATABASE_URL`. They do not use your development connection
or permit a production URL override. The test service uses temporary in-memory
storage, not the development volume.

Database tests create UUID-scoped fixtures and clean their own projects before
users; task cleanup follows the cascade. Seed tests clean their demo records.
They never truncate development tables. For a clean test database after an
interrupted run, run `npm run db:test:stop` then `npm run test:integration`;
stopping the temporary service discards its data and the runner reapplies migrations.
Do not run multiple integration suites concurrently against this single test
database, because the seed intentionally uses fixed demo IDs.

Coverage includes relational defaults, foreign keys, unique normalized email,
required/nonblank fields, enum constraints, restrict/cascade deletion, UTC date
roundtrips, transaction rollback, and a seed rerun that preserves edits and
unrelated records. These tests verify PostgreSQL behavior instead of mocking it.

## SQL to try

Phase 9 also adds a separate `devtrack_e2e` PostgreSQL service on loopback port
5434 for real browser/container workflows. It uses its own Compose project and
tmpfs storage; the E2E runner applies migrations and stops it in `finally` to
discard test data. Development (5432) and integration/coverage (5433) remain
separate. See [TESTING.md](TESTING.md) for lifecycle, guards and recovery.

Open an interactive local SQL session:

```sh
docker compose exec db psql -U devtrack -d devtrack_dev
```

List tasks with their project and owner, without selecting password hashes:

```sql
SELECT t."title", t."status", p."name" AS project, u."email" AS owner
FROM "Task" AS t
JOIN "Project" AS p ON p."id" = t."projectId"
JOIN "User" AS u ON u."id" = p."ownerId"
ORDER BY p."name", t."title";

SELECT "id", "title", "status", "priority", "dueDate"
FROM "Task"
WHERE "projectId" = '22222222-2222-4222-8222-222222222222';
```

Inspect constraints/indexes with `\d "Task"` and leave psql with `\q`.

The specification leaves descriptions, enum defaults, field naming, and deletion
actions partly open. The choices above keep the model small and follow its V1
recommendation. Database-only Compose in Phase 2 is consistent with sections 14,
65, and 116 even though Phase 10 mentions it again. There is no scope conflict.
